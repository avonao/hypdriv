# ADR 0025 — RedwoodSDK: a Worker-entry wrapper for a Vite RSC framework on Workers

**Status:** accepted · **Date:** 2026-11-01

## Context

ADR 0019 made every Vite framework a host of one runtime and one build engine; each framework supplies only the part that attaches to its own extension points. [RedwoodSDK](https://rwsdk.com) (`rwsdk` 1.x) is a React Server Components framework for Cloudflare Workers, built as a Vite plugin (`redwood()` from `rwsdk/vite`) on top of `@cloudflare/vite-plugin`. It is not a file router: an application is the Worker module `src/worker.tsx`, whose default export is `defineApp([...])` from `rwsdk/worker` — an ordered list of middleware, `route()`, `index()`, `prefix()`, `layout()`, `render(Document, [...])` and `except()` entries — and `defineApp` returns `{ __rwRoutes, fetch }`, a Worker handler object. RedwoodSDK has no `proxy.ts`, no adapter and no request hook other than that list; it runs on Workers only (its documentation names no Node or Vercel target), and it builds in several passes (the `worker` environment, an SSR pass, the client and a linker pass) into `dist/worker/index.js` + `dist/worker/wrangler.json` and `dist/client/`.

Two RedwoodSDK facts shape the integration. Every page is rendered per request, so no document is prerendered and none can carry a hash policy. And the framework generates its own CSP nonce per request (`requestInfo.rw.nonce`) and puts it on the inline scripts it renders — the RSC payload and the hydration bootstrap — in every document, while Hypdriv's nonce CSP allows only the nonce it issued.

## Decision

1. **The package is `@hypdriv/rwsdk`; the framework name is `rwsdk`, its label "RedwoodSDK".** The package follows the npm dependency (`rwsdk`), as `@hypdriv/waku` follows `waku`. A name like `@hypdriv/redwood` would read as RedwoodJS, an unrelated framework (GraphQL, Prisma, its own CLI) that Hypdriv does not support. The one consequence of the label is the health route: `/_hypdriv/health` reports `RedwoodSDK`, so `e2e/hosts` selects it with `--framework redwood` (a substring of the label), not `--framework rwsdk`.
2. **Cloudflare Workers only.** RedwoodSDK documents no other target, so `@hypdriv/rwsdk` ships the Worker integration and nothing for Vercel or Node: no adapter, no `hypdriv serve` path, no Vercel Build Output. `hypdriv init` and `hypdriv doctor` say so on another platform, and `create-hypdriv --framework rwsdk` offers Cloudflare only (`--platform vercel|node` is refused). Platform differences stay in `packages/cloudflare`; nothing in the stages changes.
3. **`withHypDriv(app)` wraps the Worker's default export.** `@hypdriv/rwsdk/worker` takes the result of `defineApp` and returns a Worker object whose `fetch` is `createWorker()` (`@hypdriv/cloudflare`) around the app's: the full Drivetrain with `runner: 'worker'` and `HTMLRewriter`, Durable Object stores when bound, `/_hypdriv/*` answered by the shell. The result keeps everything else the app has — `__rwRoutes`, so `defineLinks<typeof app>()` still types links — and `scheduled`, `queue`, `email` and `tail` take Hypdriv's jobs next to the application's own handlers (Hypdriv's dispatchers run for `scheduled`, for a queue `jobs.queues` consumes and for email when `jobs.email` is configured; the application's handler takes the rest, and a failure of either is raised after both ran). The config and the manifest come from the Vite plugin's virtual modules; `@hypdriv/rwsdk/wrap` exposes the same wrapper with both passed in, for tests and custom bundling.
4. **The assets binding is asked first.** With `assets.run_worker_first: ["/*", "!/assets/*"]` every request but RedwoodSDK's content-hashed assets reaches the Worker, so pages, server functions and `public/` files all pass the request stages. For GET and HEAD the wrapper asks the `ASSETS` binding before RedwoodSDK, so public files (`robots.txt`, images) are served as built, with the request stages and the security headers applied; a 404 from the binding falls through to the app. `assets: false` sends everything to RedwoodSDK, and another binding name can be passed with `assets: 'NAME'`.
5. **`hypdrivMiddleware()` hands RedwoodSDK the CSP nonce.** The Drivetrain's csp stage forwards the nonce it issued on the request header `x-nonce` (`security.csp.nonceHeader`) and injects it only into tags that carry none. RedwoodSDK renders its inline scripts with its own random `rw.nonce`, so they would reach the browser with a nonce the policy does not list. The middleware — the first route of `defineApp([...])` — copies the header into `rw.nonce`, and RedwoodSDK then puts Hypdriv's nonce on its RSC payload, its hydration scripts and the `<script>` tags of the application's `Document`, and `requestInfo.rw.nonce` holds the same value for tags the application renders itself. Without it the page renders but the browser blocks RedwoodSDK's scripts and the page does not hydrate; this was reproduced in a browser (without the middleware the scripts are blocked and the page stays inert; with it the page hydrates under the same policy). Because the failure is silent for the server, three things report it: the wrapper logs once per isolate when an HTML response to a request that had a nonce did not pass the middleware (the middleware leaves the marker header `x-hypdriv-rwsdk` on the response, which the wrapper removes), the build warns when the Worker entry's `defineApp` has no `hypdrivMiddleware()`, and `hypdriv doctor` fails `rwsdk.nonce-middleware` (searching `src/` when the routes live outside the entry). The check is skipped when CSP is off.
6. **The exact routes come from the running app; the build scan is best effort.** `defineApp` has no file system to read, so the Worker derives the route manifest from `__rwRoutes` (`appRoutes()` / `appManifest()`): RedwoodSDK's paths (`/users/:id/`, trailing slash, `*`) become Hypdriv patterns (`/users/[id]`, `/files/[...splat]`), a handler that renders a component is a `page` (`dynamic`, nonce CSP) and a function that returns a `Response` is a `route`; a method table (`{ get, post }`) is a page when its `get` renders. The route list is what the pipeline classifies by, so protection and CSP mode never depend on the build. The build reads the same routes from the Worker's source (`scanWorkerRoutes`: the array literals of `defineApp`, the route arrays imported from other files — relative imports and `tsconfig` paths —, `const`s, spreads, namespace members, template-literal paths) with Vite's own parser, to give the manifest `.hypdriv/manifest.json`, `hypdriv routes` and the budgets something to show before the Worker runs. A path computed at run time cannot be read statically; the build lists what it could not read and the plugin's `routes` option adds those routes (or returns the final list). Routes the build also found keep what it learned about them (client assets for Early Hints, the source file); the build id, CSP data and warnings stay the build's.
7. **The Vite plugin finishes RedwoodSDK's build.** `hypdriv()` returns three plugins, placed after `redwood()`: the host plugin of `@hypdriv/vite` (`virtual:hypdriv/config`, `virtual:hypdriv/manifest`, the Hypdriv config file) with `@hypdriv/rwsdk` forced through Vite's transform in the Worker environments; an entry plugin that, in the `worker` environment only, appends `export * from 'virtual:hypdriv/durable-objects'` to the Worker entry (the `main` of the Wrangler config, which RedwoodSDK reads, else `src/worker.tsx`, else the `entry` option) so `HypDrivLimiter`, `HypDrivIndex` and `HypDrivChannel` resolve for the Durable Object bindings without an export of the application's own (`durableObjects: false` turns it off); and a build plugin whose `buildApp` hook runs with `order: 'post'`, after all of RedwoodSDK's passes. That hook discovers the routes and the hashed client assets under `dist/client`, runs the shared finalisation (`finalizeManifest`: Early Hints data, the CSP data, Purser verification, the secrets scan, budgets — a failure fails the build), writes `.hypdriv/manifest.json`, patches the final manifest into the built Worker (`patchRuntimeManifest` on `dist/worker`, because the manifest embedded in the Worker bundle is produced before the client assets are known) and writes `dist/client/_headers` (security preset, the immutable rule for the hashed assets, Early Hints) with `writeCloudflareStatic`. Vite's `base` is honoured (RedwoodSDK nests the client output under it). There are no prerendered documents, so the manifest has none and every page is `dynamic`.
8. **`@cloudflare/vite-plugin` is declared in the project.** A config that registers it must name the environment RedwoodSDK builds the Worker in — `cloudflare({ viteEnvironment: { name: 'worker' } })` — and declare `environments: { ssr: {} }`; a config that registers nothing keeps RedwoodSDK's own registration. Declaring it gives the Worker one Wrangler config that `configPath` can point at an account-specific, git-ignored `wrangler.<name>.local.jsonc`, as the other examples do. `hypdriv doctor` fails the wrong environment or a missing `ssr` environment (`rwsdk.cloudflare-plugin`) and warns when `hypdriv()` is listed before `redwood()` (`rwsdk.plugin-order`).
9. **Request helpers are `AsyncLocalStorage` helpers.** `@hypdriv/rwsdk/server` re-exports `hyp()`, `requireHyp()`, `nonce()`, `flag()`, `geo()`, `defer()` and `jobHandler()` for route handlers, server components and server functions. They work in RedwoodSDK's RSC render because the shell establishes the context around the app's `fetch`; client components render in the browser and in the SSR bridge, not under the request.
10. **Tooling follows the other hosts.** `FrameworkName` gains `rwsdk` (label "RedwoodSDK"); `hypdriv init` wraps `defineApp` in `withHypDriv()`, puts `hypdrivMiddleware()` first, adds `hypdriv()` last to `vite.config.mts` (creating it with the `worker` environment when absent) and writes the Wrangler settings (assets binding, worker-first rule, Durable Objects); `hypdriv doctor` gets `rwsdk.worker-entry`, `rwsdk.nonce-middleware`, `rwsdk.cloudflare-plugin`, `rwsdk.plugin-order`, `rwsdk.platform` and `rwsdk.version` next to the shared Vite-host checks; `create-hypdriv --framework rwsdk` scaffolds `examples/rwsdk`; `e2e/hosts` verifies a deployed app with `--framework redwood`.

## Consequences

- One more package (`@hypdriv/rwsdk`; peers `rwsdk >=1.0.0 <2`, `vite >=8`; Node 22.12+), no change to the stages, the manifest format or the build engine. The only shared-code change is `FrameworkName`.
- RedwoodSDK 1.x is a stable release line, but the integration reads three of its internals: the shape `defineApp` returns (`__rwRoutes`, `fetch`), the environment names of its multi-pass build (`worker`, `client`) and the `rw.nonce` field of the request info. They are covered by tests that run RedwoodSDK's real build and serve it in workerd (`build.test.ts`: the nonce on every inline script, the Durable Object exports of the built Worker, the patched manifest, the static headers, the missing-middleware warning) and by wrapper and route-table tests against the real `defineApp`, so a change in RedwoodSDK fails there, not in production. `hypdriv doctor` reports a version outside the range (`rwsdk.version`).
- The nonce hand-off is a requirement the application must meet, not something the wrapper can do for it: RedwoodSDK sets `rw.nonce` before any user code runs and offers no later hook the wrapper could use. `hypdriv init`, the example, the build warning, the runtime log and `hypdriv doctor` all point at the same line; an application that turns CSP off (`security.csp.mode: 'off'`) needs no middleware.
- Route classification from the build is best effort, from the running app exact. A computed route is protected and classified correctly at run time; only the build-time manifest (`hypdriv routes` before a deploy, the budgets of routes the scan missed) depends on the `routes` option.
- Every page is rendered per request, so no page has a hash policy and the edge cache stage sees only what the application marks cacheable; this is RedwoodSDK's rendering model, not a Hypdriv limitation.
- Cloudflare only: the Vercel and Node rows of the host matrix stay empty for RedwoodSDK until the framework documents those targets. An application that wants Node or Vercel uses another host.
- `vite preview` proxies requests with `sec-fetch-mode: cors`, so the bot-shield check of `e2e/hosts` and `hypdriv audit` reports a failure that is not one under preview (a `curl` user agent no longer looks like a navigation); `wrangler dev` on the built `dist/worker/wrangler.json` and deployments do not have the artifact.
- Verified locally: a real RedwoodSDK build (the unit suite builds the example-shaped app and serves it), the production Worker in workerd through `vite preview` and `wrangler dev` on the built Wrangler config, `vite dev`, a browser run that hydrates the page with the nonce hand-off and reports no CSP violation, the negative run without the middleware, `hypdriv audit all` and the `e2e/hosts` check. Live Cloudflare deployments (colo behaviour, Early Hints at the edge, zone purges, Durable Objects at scale), server functions driven from a browser and HMR over the dev WebSocket need a real account or a longer browser session and remain pending (`docs/preview-status.md`).
