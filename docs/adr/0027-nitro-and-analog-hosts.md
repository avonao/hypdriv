# ADR 0027 — Nitro and Analog: one shared Nitro layer, one Angular host

**Status:** accepted · **Date:** 2026-11-01

## Context

ADR 0019 made every Vite framework a host of one runtime (`createHandler()`) and one build engine (`@hypdriv/build` through `@hypdriv/vite`); ADR 0020 did the same for server frameworks without a build step. Two more targets sit on [Nitro](https://nitro.build), the server engine of Nuxt, Analog, SolidStart, TanStack Start and standalone servers:

- **Nitro itself**, in two generations that are not API-compatible. Nitro 2 (`nitropack` 2.13) is built on h3 1.x and Rollup, takes `modules` in `nitro.config.ts`, and hands the application a Nitro app (`h3App`) its plugins can wrap. Nitro 3 (`nitro` `3.0.261029-rc`) is built on h3 2.x (Web `Request` / `Response`) and Rolldown, ships a Vite plugin (`nitro/vite`) that builds the client and the server in one `vite build`, and wraps the application as a `fetch` handler.
- **[Analog](https://analogjs.org)**, the Angular meta-framework. Analog 2.9 is a Vite plugin (`@analogjs/platform`) that builds Angular's client and server-rendering bundles, runs Nitro 2 inside the Vite build (`dist/analog`), takes the Nitro configuration through `analog({ nitro })`, and routes `src/app/pages/**/*.page.ts` and `*.md` content files. Analog 3 (beta) moves to Nitro 3.

Nuxt (`@hypdriv/nuxt`, earlier) already integrates with Nitro 2 through Nuxt's own module system, with the Nitro-level pieces (capturing a Nitro response, running the pipeline around it, reading prerendered documents, the Cloudflare entry) written inside that package.

## Decision

1. **Two packages: `@hypdriv/nitro` (shared) and `@hypdriv/analog` (Angular).** Everything that depends on Nitro and not on a framework lives in `@hypdriv/nitro`: the request hook for Nitro 2 and Nitro 3, the capture response, the Cloudflare Worker entry, prerendered-document discovery, manifest finalisation and the static header rules for the Nitro output. Everything that depends on Analog lives in `@hypdriv/analog`: the Angular file router and content routes, `provideHypDriv()` (CSP nonce, request context), the browser-safe `injectHyp()`, and the Vite plugin that reads Analog's client build. A plain Nitro server, a Nitro 3 + Vite app and Analog are therefore three consumers of one module, and a Nitro-based framework added later is a thin package (route discovery plus the framework's own helpers) rather than a third copy.
2. **One package for Nitro 2 and Nitro 3, one runtime per generation.** The decisions that do not depend on the generation — the module, option handling, target detection from the preset, route discovery, finalisation, static headers, the ALS request context (`@hypdriv/nitro/server`) — are shared. The two request hooks differ in what they wrap and are separate files (`runtime/nitro2`, `runtime/nitro3`); the module picks one from `nitro.meta.majorVersion` and registers it as a Nitro plugin. `nitropack >=2.12 <3`, `nitro >=3.0.0-rc <4` and `vite >=8` are optional peers, so an application installs only the one it uses. The alternative of `@hypdriv/nitro2` and `@hypdriv/nitro3` was rejected: everything after the hook is identical, Analog 3 moves from one generation to the other, and an application that upgrades Nitro should keep one Hypdriv dependency and one configuration.
3. **A Nitro module, not a patch.** `hypdrivNitro()` is a Nitro module (`modules: [...]` in `nitro.config.ts`, or `nitro.modules` in Analog, or the `nitro` key of the Vite plugin `hypdriv()` from `@hypdriv/nitro/vite` for Nitro 3). It uses Nitro's documented hooks (`build:before`, `rollup:before`, `prerender:done`, `compiled`, `vite:compile:before`), virtual modules and plugins. Nothing of Nitro, Rollup, Rolldown, Vite or h3 is patched.
4. **The hook wraps the request handler; Nitro's prerender instance is not wrapped.** Request stages run first and may answer on their own; otherwise Nitro renders into a capture response inside the request's `AsyncLocalStorage` context and the response stages post-process the captured head and streaming body (`createHandler({ runner: 'host' })`). Errors are rendered by Nitro's error handler inside the same capture. Prerendered files carry no request's nonce.
5. **Platforms.** `cloudflare-module` gets Hypdriv's Worker entry (`createWorker()` around Nitro, the Hypdriv Durable Objects exported next to the application's own `cloudflare.exports`, `scheduled` / `queue` / `email` dispatch, GET/HEAD answered from the assets binding first); other Cloudflare presets use the in-app hook. `vercel` runs the pipeline inside the function and adds Routing Middleware for the prerendered pages the CDN serves without it, with the static header rules as Build Output routes. `node-server` runs the pipeline for every request except immutable build assets. Static presets are left alone. Hashed assets under the client `assetsDir` get an immutable `Cache-Control` through Nitro's own mechanisms (`publicAssets` with `maxAge` on Nitro 2, the route rules Nitro adds for the client `assetsDir` on Nitro 3), and the module removes Vite's `.vite/manifest.json` from the public output once it has read it.
6. **Routes are read from the sources.** The module reads Nitro's scanned handlers and renderer and the prerendered documents (`prerender:done`, with the files on disk as the fallback); a framework supplies page routes through `isPage`, `routes`, `internalPages` and `pageAssets`. Analog supplies its file router (`.page.ts`, `(group)` folders, `[param]`, `[...catchall]`, content routes) and the client build's per-page assets. A prerendered document served as built (Workers Static Assets, the Vercel CDN) gets a hash CSP; a page rendered per request gets a nonce CSP; both are classified in `.hypdriv/manifest.json`.
7. **The Angular integration is two small entries.** `@hypdriv/analog/angular/server` (`provideHypDriv()`, `injectNonce()`) belongs in `app.config.server.ts` and provides Angular's `CSP_NONCE`, an `ngCspNonce` attribute on the root element for the browser-side Angular, and the request context. `@hypdriv/analog/angular` has no runtime dependency on Hypdriv and holds `injectHyp()` and its token, so a component can import it without pulling the runtime into the browser bundle. Pages hand request-dependent facts to hydration with Angular's `TransferState`; the guide shows the pattern. Zone.js can drop the ALS context; the nonce then comes from the `x-nonce` request header.
8. **Tooling follows the other hosts.** `FrameworkName` gains `nitro` and `analog`; `hypdriv init` edits `nitro.config.ts` / `vite.config.ts` (including Analog's arrow-function form); `hypdriv doctor` gets `nitro.cloudflare-preset`, `analog.tsconfig-emit` and `analog.server-providers` (category `nitro`) next to the shared Vite-host checks; `create-hypdriv --framework nitro|analog` scaffolds `examples/nitro` (Nitro 2) and `examples/analog` for every platform, and `examples/nitro-vite` is the Nitro 3 variant; `e2e/hosts` verifies a deployed app with `--framework nitro|analog` (both Nitro examples report `nitro`).

## Consequences

- Two packages (`@hypdriv/nitro`, `@hypdriv/analog`) and three examples (`examples/nitro`, `examples/nitro-vite`, `examples/analog`), each built for Cloudflare, Vercel and Node with `HYPDRIV_TARGET`. No change to the stages, the manifest format or the build engine; the only shared-code change is `FrameworkName`.
- Nitro 3 is a release candidate (`3.0.261029-rc`) and Analog 3 a beta. The peer ranges allow them, and the Nitro 3 behaviour is tested against the real packages: unit tests for the module, a real `nitro build` for each preset in `examples/nitro-vite`, and the examples served under Node, workerd (`wrangler dev` on the built output) and an in-process emulation of Vercel's routing. Analog 3 is inside the peer range but has not been exercised.
- Nitro 2 buffers responses on Cloudflare (`localFetch`), so streaming SSR and event streams there arrive in one piece; Node and Vercel stream. WebSocket upgrades go to Nitro directly on Cloudflare. Cloudflare's `_headers` holds at most 100 rules; documents beyond that are reported at build time and get their CSP from the Worker.
- Nitro-cached renders (`routeRules` with `swr` or `cache` on an SSR route) hold the first request's nonce; the pipeline re-stamps the document, but a framework's own nonce attributes keep the first value. Prerendering such routes is the answer.
- `vite dev` for Analog renders pages with Vite's own server-side rendering, outside Nitro; the pipeline covers the Nitro server (API routes) and `/_hypdriv/*` there.
- `@hypdriv/nuxt` (earlier than this change) had written the Nitro 2 engine — capture response, hook, request helpers, prerendered paths and the Cloudflare Worker — inside its own package. Those six runtime files are now shims over `@hypdriv/nitro` (`@hypdriv/nitro/runtime/nitro2/*`, `runtime/prerendered`, exported with a `source` condition so tests run on `src/`), and Nuxt keeps what is Nuxt's: the Nuxt module, the Nitro plugin (its option shape and the `nuxt` host label), `nuxtSkip`, the composables and the nonce plugin. Nuxt's own tests (64) are unchanged and pass, and `examples/nuxt` gives the same results as before on Node, workerd and the Vercel emulation, and in `nuxt dev`. Two things the move required of the Nuxt module: the engine's directory is bundled and excluded from Nitro's auto-imports like the module's own runtime directory, and Hypdriv's packages are aliased to the files the module resolves in builds too (they were in dev only), because Nitro does not resolve them from the engine in a linked workspace.
- Verified locally on Node (real servers), workerd and a real `vercel build` with Vercel's routing emulated in process; live Cloudflare and Vercel runs (zone and platform services, Routing Middleware) remain pending (`docs/preview-status.md`).
