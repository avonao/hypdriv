# ADR 0021 — Waku: a server-entry adapter for a Vite RSC framework

**Status:** accepted · **Date:** 2026-11-01

## Context

ADR 0019 made every Vite framework a host of one runtime (`createHandler()`) and one build engine (`@hypdriv/build` through `@hypdriv/vite`); each framework supplies only the part that attaches to its own extension points. [Waku](https://waku.gg) (1.0 release candidates) is a minimal React Server Components framework on Vite (`@vitejs/plugin-rsc`) with a file router (`src/pages`), a programmatic router (`createPages`), server functions, `_api` route handlers and prerendering. Its deployment contract is the **server-entry adapter**: `unstable_createServerEntryAdapter` builds an adapter (`waku/adapters/node|vercel|cloudflare|…`) that returns `{ fetch, build, buildOptions, buildEnhancers, serve, defaultExport }`, selected with `unstable_adapter` in `waku.config.ts` or imported by a project's own `src/waku.server.tsx`. Waku is not Next.js, Astro or a Hono app: it has no `proxy.ts`, no request hook other than the adapter, and its Cloudflare and Vercel builds are produced by build enhancers that write `dist/server/wrangler.json`, `.wrangler/deploy/config.json` and `.vercel/output`.

## Decision

1. **`@hypdriv/waku` wraps Waku's own adapters.** `@hypdriv/waku/adapters/node|vercel|cloudflare` import the matching Waku adapter, call it with the application's handlers and options, and return the same server entry with `fetch` behind `createHandler({ runner: 'host' })`. The adapter's `build`, `buildOptions`, `buildEnhancers`, `serve` and `defaultExport` are Waku's; nothing of Waku, Vite or Hono is patched. The Hypdriv options travel next to Waku's (`adapter(handlers, { …wakuOptions, hypdriv: {…} })`).
2. **`withHypDriv(config)` selects the adapter and adds the plugin.** It sets `unstable_adapter` to the adapter of the build's target (never over one the application set) and appends the Vite plugin. The target is `HYPDRIV_TARGET`, else Cloudflare when `@cloudflare/vite-plugin` is among the Vite plugins, else `VERCEL=1`, else `CLOUDFLARE` / `WORKERS_CI`, else Node; Netlify and the other platforms keep Waku's own adapter. The config wrapper and the build plugin resolve the target by one function, so they cannot disagree. A Cloudflare target without the Cloudflare plugin fails with the line to add.
3. **Managed mode is the default and keeps working.** A project without `src/waku.server.*` (Waku's managed mode) needs no file: Waku's virtual entry loads the adapter `unstable_adapter` names. A project with its own entry imports the Hypdriv adapter instead of Waku's.
4. **The plugin serves the adapters' inputs and finishes the build.** `virtual:hypdriv/config` and `virtual:hypdriv/manifest` are what the adapters import; the config is the `hypdriv.config.ts` of the project. After the complete build — Waku's static generation and the platform enhancer's output included, ordered by a `buildApp` hook with `order: 'post'` — the plugin discovers the routes, prerendered documents and hashed assets, writes `.hypdriv/manifest.json`, patches the final manifest into every server output and writes the platform's static layer (`finalizeManifest`, `rulesFor`, `patchRuntimeManifest`, `writeCloudflareStatic`, `writeVercelStatic`, `addVercelMiddleware`).
5. **Routes are read from the sources, not run.** `src/pages` follows Waku's file router (`_api`, `_layout`, `_root`, `_slices`, `_interceptors`, `(group)` folders, `[slug]`, `[...wild]`, `export const getConfig = … render: 'static' | 'dynamic'`, `staticPaths`); the literal `createPage` / `createApi` calls of `src/waku.server.*` are added, and computed paths go in the `routes` option. A static page is prerendered, a static slug page only with `staticPaths`; everything else is dynamic and gets a nonce CSP. Prerendered documents the platform serves as built (Workers Static Assets, the Vercel CDN) get a hash CSP; on Node they are served from inside the wrapped server, so the pipeline decorates them.
6. **Cloudflare.** The Worker's default export is `createWorker()` around Waku's: the full Drivetrain with `HTMLRewriter`, Durable Object stores, `scheduled` / `queue` / `email` / `tail` handlers next to the application's own `handlers`, and GET/HEAD requests answered from the assets binding first. Waku's Cloudflare build calls its own adapter in the build with a loopback request (`/__waku_internal_build_static_files`) to generate static files; that request goes to Waku directly (loopback host and no `cf-visitor` header), so the generated files carry no request's nonce. The Durable Object classes are exported from the Worker entry by a transform on Waku's `entry.server.js` (appended to the RSC environment only, once), and in `wrangler dev` / `vite dev` — where `@cloudflare/vite-plugin` loads the wrangler `main` (`./src/waku.server`) in workerd — a virtual worker entry stands in for a `main` the project does not have. Waku's own lookup of `/src/waku.server` is never matched, so a project file always wins.
7. **Vercel.** Waku's adapter writes one function (`RSC.func`) with a catch-all route; Hypdriv wraps its `fetch`. Prerendered documents the build leaves in `.vercel/output/static` are mapped to clean URLs with Build Output `overrides` (the CDN answers `/about` from `about/index.html`), get the static header rules and the hash CSP, and run the request stages through Hypdriv's prerender-scoped Routing Middleware. Everything else reaches the function, which runs the pipeline once.
8. **Node.** Waku's Node adapter is a Hono app that serves `dist/public` and then the RSC middleware; the wrapper sits around that app's `fetch`, so static files, RSC payloads and pages all pass the pipeline, and hashed assets get the immutable `Cache-Control` Waku's static server omits.
9. **Request helpers are `AsyncLocalStorage` helpers.** `@hypdriv/waku/server` re-exports `hyp()`, `requireHyp()`, `nonce()`, `flag()`, `geo()`, `defer()` and `jobHandler()` for server components, server functions and `_api` routes. `hyp()` returns `null` outside a request (the build-time prerender), as in the other hosts.
10. **Tooling follows the other hosts.** `FrameworkName` gains `waku`; `hypdriv init` adds `withHypDriv` (and the Cloudflare plugin and wrangler settings) to `waku.config.ts`; `hypdriv doctor` gets `waku.adapter`, `waku.cloudflare-plugin`, `waku.worker-main` and `waku.version` next to the shared Vite-host checks; `create-hypdriv --framework waku` scaffolds `examples/waku` for every platform; `e2e/hosts` verifies a deployed Waku app with `--framework waku`.

## Consequences

- One more package (`@hypdriv/waku`; peers `waku >=1.0.0-rc.4 <2`, `vite >=8`), no change to the stages, the manifest format or the build engine. The only shared-code change is `FrameworkName`.
- Waku's adapter API is `unstable_`-prefixed and Waku is a release candidate: the package pins the peer range, `hypdriv doctor` reports a pre-release (`waku.version`), and the managed-entry, build-request and `entry.server.js` assumptions are covered by tests that run Waku's real build for Node and Vercel (`build.test.ts`, which also serves the Node build in its own process) and by Worker-wrapper tests, so a change in Waku fails there, not in production. The Cloudflare build is verified with `wrangler dev` on the built `dist/server/wrangler.json`, not in the unit suite (it needs workerd and the Cloudflare Vite plugin).
- Routes are discovered statically. A programmatic route whose path is computed is not in the manifest unless listed in the `routes` option; its pages are still served and protected (the pipeline runs for every request), only classification and CSP mode fall back to "rendered per request".
- Hono is Waku's own server layer (a transitive dependency, `4.13.16` at the time of writing); Hypdriv does not import it.
- Verified locally on Node (a real server), workerd (`wrangler dev` on the built `dist/server/wrangler.json`) and a real `vercel build` with the Vercel routing emulated in process; live Cloudflare and Vercel runs remain pending (`docs/preview-status.md`).
