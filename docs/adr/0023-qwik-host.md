# ADR 0023 — Qwik: Qwik Router adapters and server entries on Vite

**Status:** accepted · **Date:** 2026-11-01

## Context

ADR 0019 made every Vite framework a host of one runtime (`createHandler()`) and one build engine (`@hypdriv/build` through `@hypdriv/vite`); each framework supplies only the part that attaches to its own extension points. [Qwik](https://qwik.dev) (v2 release candidates, `@qwik.dev/core`) with Qwik Router (`@qwik.dev/router`: file routes, `routeLoader$`, `routeAction$`, `server$`, middleware and endpoints) is a resumable framework on Vite. Its deployment contract has three parts that map onto the three things a host needs:

- **Platform adapters** are Vite plugins written with `viteAdapter()` (`@qwik.dev/router/adapters/shared/vite`). A server build is a second Vite build (`vite build -c adapters/<name>/vite.config.ts`) whose adapter runs Qwik's static generation after bundling and writes the platform's output; the adapter's plugin name is `vite-plugin-qwik-router-ssg-<name>`.
- **Server entries** (`src/entry.<platform>.tsx`) create the router with a platform middleware (`createQwikRouter` of `@qwik.dev/router/middleware/node|cloudflare-pages|vercel-edge`) around the `render` function of `src/entry.ssr.tsx`, which is the application's code.
- **Qwik Router's Vite plugin** exposes the route table and the base path (`api.getRoutes()`, `getBasePathname()`), and the optimizer plugin the client and server output directories.

Qwik has no `proxy.ts`, no request hook outside the entry and no module system to register a plugin with. Its v1 line (`@builder.io/qwik-city`) predates Vite 8.

## Decision

1. **`@hypdriv/qwik` replaces the platform's middleware and adapter with its own, built from Qwik's.** `@hypdriv/qwik/middleware/node|vercel|cloudflare` export `createQwikRouter()` with the shape of Qwik's own: they call Qwik Router's `requestHandler` (the function every Qwik adapter calls, with the same request event, streaming and request body limit) behind a Web `fetch`, and put it behind `createHandler({ runner: 'host' })`. `@hypdriv/qwik/adapters/node|vercel|cloudflare` are `viteAdapter()` plugins: static generation, the static path list and the cleanup of generated files are Qwik's; Hypdriv adds the platform output and the SSG origin fallback (`site.origin`). Nothing of Qwik, Qwik Router, Vite or Rolldown is patched, and the Hypdriv options travel next to Qwik's (`createQwikRouter({ render, hypdriv: {…} })`).
2. **Qwik v2 only.** The peer range is `@qwik.dev/core` and `@qwik.dev/router` `>=2.0.0-rc.4 <3` with Vite 8 and Node 20.19+. Qwik City 1.x peers Vite below 8 and has a different adapter API; wrapping both would double the surface for a line that is being migrated away from. `hypdriv init` and `hypdriv doctor` (`qwik.version`) detect v1 and point to `qwik migrate-v2`.
3. **Three pieces, each in the place Qwik already has for it.** The `hypdriv()` plugin sits next to `qwikRouter()` and `qwikVite()` in `vite.config.ts`; the adapter replaces Qwik's in `adapters/<target>/vite.config.ts`; the entry imports `createQwikRouter` from Hypdriv's middleware. Qwik's own `nonce` render option stays unused: the csp stage injects the nonce into the streamed HTML (`HTMLRewriter` on Workers, a streaming injector elsewhere), as in the other hosts.
4. **The target is the adapter that builds the server.** The plugin reads the adapter plugin by name (`hypdriv-node|vercel|cloudflare`, and Qwik's `node-server`, `vercel-edge`, `cloudflare-pages`) and falls back to `detectTarget()` (`HYPDRIV_TARGET`, `VERCEL=1`, `CLOUDFLARE` / `WORKERS_CI`, else Node); the `target` option overrides both. What is built wins over the environment. Qwik's adapters for other platforms (Netlify, AWS Lambda, Deno, Bun, static) are not wrapped.
5. **The plugin finishes the build.** `virtual:hypdriv/config` and `virtual:hypdriv/manifest` are what the entries import. A `buildApp` hook with `order: 'post'` runs after Qwik's static generation and the adapter's output: the plugin takes the routes from Qwik Router's route table (`.tsx`, `.jsx`, `.md`, `.mdx` are pages, `.ts` and `.js` are endpoints), finds the prerendered documents in the client output, writes `.hypdriv/manifest.json` (`finalizeManifest`), patches the final manifest into every server output (`patchRuntimeManifest`) and writes the platform's static layer (`rulesFor`, `writeCloudflareStatic`, `writeVercelStatic`, `addVercelMiddleware`). Prerendered documents are the static layer's (`documentsServedStatically`): they get a hash CSP; everything else Qwik renders is dynamic and gets a nonce CSP. A dynamic route with `onStaticGenerate` stays dynamic and the concrete paths Qwik prerendered for it are promoted to static page routes of their own, so each has a hash policy and the route keeps the rest.
6. **Route loader data is application data.** Qwik serves loader results from `<page>/q-loader-<id>.<hash>.json`, which the Cloudflare runner's file-like-path rule (`cloudflare.skipStaticAssets`) would skip. The example and the `init` template set `skipStaticAssets: false`; `hypdriv doctor` (`qwik.loader-json`) reports a config that leaves it on. The Node, dev and Vercel runners never treat it as a file.
7. **Cloudflare.** The default export of `src/entry.cloudflare.tsx` is `createWorker()` around Qwik's request handler: the Drivetrain with `HTMLRewriter`, Durable Object stores, `scheduled` / `queue` / `email` / `tail` handlers next to the application's own, and GET/HEAD requests answered from the assets binding first. The adapter writes `dist/_worker.js`, a module that re-exports the server bundle, so `wrangler.jsonc` keeps `main` at `./dist/_worker.js` with the client build in `dist` as the assets directory (`run_worker_first: ["/*", "!/build/*", "!/assets/*"]`). The Durable Object classes are exported from the Worker entry by a transform on the server build's input modules (once), through a virtual module that resolves to `@hypdriv/qwik/durable-objects` from the plugin's own dependencies.
8. **Vercel.** The adapter's server build goes to `.vercel/output/functions/_qwik-router.func` (`build.outDir`, Qwik's rule for Build Output adapters), with a Node.js function config (Web handler, response streaming) and a catch-all route; the client build becomes `.vercel/output/static`. Prerendered documents are served by the CDN with the static header rules and their hash CSP and run the request stages through Hypdriv's prerender-scoped Routing Middleware; everything else reaches the function, which runs the pipeline once and sets the skew-protection cookie like Qwik's own adapter.
9. **Node.** The entry serves the client build (the static handler of `@hypdriv/vite/node`, with the hashed prefixes the manifest names, `/build/` and `/assets/`) and Qwik's request handler behind one listener: prerendered pages, hashed files and public files pass the pipeline, and the hashed files get `Cache-Control: public, max-age=31536000, immutable`. `router`, `staticFile` and `notFound` keep the shapes of Qwik's Node middleware.
10. **The dev server gets the pipeline.** `vite --mode ssr` runs Hypdriv's middleware registered directly in `configureServer` (before Qwik Router's post hook) around everything Vite does not serve itself, with the development manifest of the live route table.
11. **Request helpers are `AsyncLocalStorage` helpers.** `@hypdriv/qwik/server` re-exports `hyp()`, `requireHyp()`, `nonce()`, `flag()`, `geo()`, `defer()` and `jobHandler()` for loaders, actions, `server$`, middleware and endpoints. `hyp()` returns `null` outside a request (the build-time prerender), as in the other hosts. `requestEv.clientConn` carries the client address and country the pipeline resolved.
12. **Tooling follows the other hosts.** `FrameworkName` gains `qwik`; `hypdriv init` adds the plugin to `vite.config.ts` (function-form configs included, which Qwik's starter uses) and writes the adapter, entry and wrangler settings of the chosen platform; `hypdriv doctor` gets `qwik.version`, `qwik.vite`, `qwik.adapter`, `qwik.entry`, `qwik.worker`, `qwik.vercel-outdir` and `qwik.loader-json` next to the shared Vite-host checks; `create-hypdriv --framework qwik` scaffolds `examples/qwik` for every platform; `e2e/hosts` verifies a deployed Qwik app with `--framework qwik`.

## Consequences

- One more package (`@hypdriv/qwik`; peers `@qwik.dev/core` and `@qwik.dev/router` `>=2.0.0-rc.4 <3`, `vite >=8`), no change to the stages, the manifest format or the build engine. The shared-code changes are `FrameworkName`, two fixes found while building the host (`sendWebResponse` in `@hypdriv/vite/node` preserves the response's `statusText`; `hypdriv init` edits function-form Vite configs) and a Biome override for `packages/qwik/**` that turns off Qwik's own lint rule for lexical scope (`useQwikValidLexicalScope`, which assumes application code) for this library.
- Qwik v2 is a release candidate: the package pins the peer range, `hypdriv doctor` reports the pre-release (`qwik.version`), and the assumptions about Qwik's adapter output (plugin names, `generate` timing, the static path list, the Build Output layout) are covered by tests that run Qwik's real Node and Vercel builds (`build.test.ts`, which also serves the Node build in its own process and invokes the built Vercel function), so a change in Qwik fails there, not in production. The Cloudflare build is verified with `wrangler dev` on the built Worker, not in the unit suite (it needs workerd).
- Two upstream warnings stay in the build log: Qwik Router's "SSG was skipped" from the plugin instance of the server environment (static generation runs regardless) and Rolldown's `INEFFECTIVE_DYNAMIC_IMPORT` for `@qwik.dev/router`.
- Routes come from Qwik Router's route table, so they are exactly what Qwik serves; only the classification of dynamic routes depends on what the build prerendered. `vite preview` serves hashed files through Vite's static server, which answers them `no-cache`: the pipeline decorates documents and endpoints there, and the immutable caching of hashed files is the Node entry's.
- Verified locally on Node (a real server, `vite preview` and the dev server), workerd (`wrangler dev` on the built Worker) and a real `vercel build` with the function invoked in process and the Vercel routing emulated. No browser was available, so hydration and SPA navigation under the CSP were not exercised; live Cloudflare and Vercel runs remain pending (`docs/preview-status.md`).
