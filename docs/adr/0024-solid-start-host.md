# ADR 0024 — SolidStart 2: a Nitro runtime plugin and a Worker shell behind deployment plugins

**Status:** accepted · **Date:** 2026-11-01

## Context

ADR 0019 made every Vite framework a host of one runtime (`createHandler()`) and one build engine (`@hypdriv/build` through `@hypdriv/vite`); each framework supplies only the part that attaches to its own extension points. [SolidStart 2](https://docs.solidjs.com/solid-start/v2) (2.1.0) is Solid's meta-framework rebuilt on Vite 8. It has no adapter API of its own: the `solidStart()` Vite plugin defines the `client` and `ssr` Vite environments, and **deployment plugins** turn them into a server — Nitro 3 (`nitro/vite`, with a preset per platform: `node-server`, `vercel`, `cloudflare_module`, …) or `@cloudflare/vite-plugin` with `viteEnvironment: { name: 'ssr' }`. The application's server entry is `src/entry-server.tsx`, whose default export is `createHandler(fn, options)` — an H3 v2 app with a `fetch` method; `options.nonce` flows to Solid's `renderToStream`. File routes live in `src/routes` (`[id]`, `[[id]]`, `[...rest]`, `(group)` folders, a page with child pages is a layout, HTTP-method exports make an API route), server functions are served under `/_server`, client assets under `/_build/assets`, and the only static generation is **Nitro's prerendering** (`nitro.prerender.routes`).

SolidStart is not Next.js, Astro or a Hono app: there is no `proxy.ts`, no middleware contract that sees every response, and the server a deployment runs is not SolidStart's but Nitro's (or the Worker the Cloudflare plugin builds from a file the application writes).

## Decision

1. **A Nitro module carries the runtime plugin.** The Vite plugin `hypdriv()` from `@hypdriv/solid-start/vite` exposes a Nitro module (`plugin.nitro`), which Nitro installs when it initialises. The module registers a Nitro runtime plugin (`@hypdriv/solid-start/nitro`) that wraps `nitroApp.fetch` — the one function every request of every Nitro preset passes through, prerendered documents and public files Nitro serves itself included — with `createHandler({ runner: 'host' })`. The request SolidStart sees is the pipeline's forwarded request carrying the original request's srvx facts (`ip`, `waitUntil`, `runtime`, `context`, `cf`). Nothing of SolidStart, Nitro, H3 or Vite is patched.
2. **The virtual modules come from `nitro.options.virtual`.** `virtual:hypdriv/config`, `virtual:hypdriv/manifest` and `virtual:hypdriv/solid-start` (target, development flag, hashed-asset prefixes) are registered there, so the server bundle and Nitro's prerender build resolve the same modules. Nitro's prerender instance (preset `nitro-prerender`) is skipped by the module, so prerendered documents never run the pipeline and carry no per-request nonce, id or flag; the build fails if a prerendered document contains a `nonce` attribute.
3. **Cloudflare through `@cloudflare/vite-plugin`: the Worker is the application's file.** SolidStart's `entry-server` is not a Worker entry, and the plugin's `main` must be a module the application owns. `@hypdriv/solid-start/cloudflare` provides `createSolidStartWorker({ config, manifest, entry })`, which puts Hypdriv's Worker shell (`createWorker()` from `@hypdriv/cloudflare`: the Drivetrain with `HTMLRewriter`, Durable Object stores, `scheduled` / `queue` / `email` / `tail` handlers) around `entry: () => import('./entry-server')` — the entry is passed in by the application so Vite loads it once. GET/HEAD requests are answered from the assets binding first (so `run_worker_first` gives public files the request stages), and `env` / `ctx` reach SolidStart on `request.runtime.cloudflare`, as srvx provides them on every other runtime. With Nitro's own `cloudflare_module` preset the Nitro runtime plugin runs in the Worker instead.
4. **The nonce reaches Solid through `createHandler`'s options.** `hypdrivStart()` (`@hypdriv/solid-start`) is the render-options argument: it reads the request's nonce from the Drivetrain's context and returns `{ nonce }`, so Solid stamps it on its hydration script, the serialised-resource scripts it streams and the client redirect it writes. Without it the CSP stage's streaming injector still nonces every `<script>` of the response; with it the rewrite finds nothing left to do. Prerender renders have no context, hence no nonce.
5. **The build finishes after Nitro.** A `buildApp` hook with `order: 'post'` runs once the client and server environments, Nitro's server build and its prerendering are done (and fails the build with the line to fix when `hypdriv()` is listed before `nitro()`). It reads the prerendered documents from Nitro's public output (or the client build without Nitro), writes `.hypdriv/manifest.json`, patches the final manifest into every server output (`dist/server`, `.output/server`, `.vercel/output/functions`) and writes the platform's static layer: Cloudflare `_headers`, Vercel Build Output header routes and clean-URL `overrides` plus Routing Middleware for the prerendered pages, Nitro `routeRules` for a Node server's hashed assets.
6. **Routes are read from the sources.** `src/routes` is scanned with SolidStart's own conventions (extension list and `appRoot` / `routeDir` from `solidStart()`'s options); a layout is not a route, its child pages are; `(group)` folders are dropped and SolidStart's route ids (`:id`, `:id?`, `*rest`) become Hypdriv's `[id]`, `[[id]]` and `[...rest]` patterns (parameter names such as `404` are sanitised for the matcher); a module with HTTP-method exports and no page is an `endpoint`; `"use server"` anywhere in the app adds the `/_server/[[...path]]` endpoint. Per-route client assets come from the client Vite manifest, whose route chunks are keyed `src/routes/about.tsx?pick=default&…`. Prerendered pages are `static` (hash CSP); everything else is `dynamic` (nonce CSP).
7. **Targets.** Node: Nitro serves prerendered documents from inside `nitroApp.fetch`, so the pipeline decorates them with the hash CSP from the manifest (`documentsServedStatically: false`), while content-hashed assets skip the pipeline and get their headers from Nitro route rules. Vercel and Cloudflare serve prerendered documents as files (`documentsServedStatically: true`) with static header rules, plus the prerender-scoped Routing Middleware on Vercel. Nitro's Node server also publishes `/.vite/manifest.json` from its public directory; the wrapper answers `404` for `/.vite/*` and `/.hypdriv/*`.
8. **Request helpers are `AsyncLocalStorage` helpers.** `@hypdriv/solid-start/server` re-exports `hyp()`, `requireHyp()`, `nonce()`, `flag()`, `geo()`, `defer()` and `jobHandler()` for API routes, server functions and route `preload` / `createAsync` code while it renders on the server; the `browser` export condition resolves to stand-ins, because route components also run in the browser.
9. **Tooling follows the other hosts.** `FrameworkName` gains `solid-start`; `hypdriv init` registers `hypdriv()` after `solidStart()` and the deployment plugin in `vite.config`, passes `hypdrivStart()` to `createHandler()` and writes the Worker entry and wrangler settings on Cloudflare; `hypdriv doctor` gets `solid-start.version`, `.deployment-plugin`, `.plugin-order`, `.cloudflare-plugin`, `.worker-entry`, `.entry-nonce` and `.prerender` next to the shared Vite-host checks; `create-hypdriv --framework solid-start` scaffolds `examples/solid-start` for every platform; `e2e/hosts` verifies a deployed SolidStart app with `--framework solid-start`.

## Consequences

- One more package (`@hypdriv/solid-start`; peers `@solidjs/start >=2.0.0 <3`, `vite >=8`), no change to the stages, the manifest format or the build engine. The only shared-code change is `FrameworkName`.
- Nitro 3 is a release candidate (`3.0.261029-rc` at the time of writing) and the module, virtual-module and runtime-plugin assumptions are tested against its real builds: `build.test.ts` runs three Vite builds (Vercel with the function called in process, Node with the server spawned, and Nitro's `cloudflare_module` with the embedded manifest and `_headers` checked), so a change in Nitro or SolidStart fails there, not in production.
- SolidStart prerenders only through Nitro. On `@cloudflare/vite-plugin` every page renders per request and carries a nonce-based CSP; a project that needs prerendered pages on Workers builds with Nitro's `cloudflare_module` preset (static assets, hash CSP from `_headers`) and gives up the Hypdriv Worker shell there: Durable Object stores, `scheduled` / `queue` / `email` handlers and `run_worker_first` for public files need the shell.
- `vite preview` does not run a SolidStart build (its dev-server plugin looks for SolidStart's own server entry); the local production run is `node .output/server/index.mjs` (Node), `wrangler dev -c dist/server/wrangler.json` (Cloudflare) and `vercel build` (Vercel).
- Routes are discovered by reading sources with a lexical scanner: `export * from` in a route module is not followed, and nothing is classified `isr` (no route rules or revalidation for SolidStart pages yet), so pages are `static` (prerendered) or `dynamic`.
- Verified locally on Node (a real server with the live checks and `hypdriv audit all`), workerd (`wrangler dev` on the built `@cloudflare/vite-plugin` Worker and on a Nitro `cloudflare_module` Worker) and a real offline `vercel build` with the Vercel routing emulated in process; live Cloudflare and Vercel runs remain pending (`docs/preview-status.md`).
